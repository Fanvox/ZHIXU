# 知序 Zhixu

**AI-Powered Knowledge Graph & Learning Companion**

> 知識を断片から体系へ、学びを受動的な受容から能動的な探求へ。

[简体中文](README.md) · [English](README.en.md) · **日本語** · [한국어](README.ko.md)

> **現在のバージョン：v2.2.0** — 変更履歴は [CHANGELOG.md](CHANGELOG.md) をご覧ください

知序は **AI ナレッジグラフ** を中核とする個別最適化学習プラットフォームです。散在する講義資料（PDF / DOCX / PPTX / TXT / Markdown）を、可視化・探索・追跡が可能な知識体系へと変換し、知識の盲点診断と個別学習パスを通じて、学生が知識ポイント同士のつながりを真に理解できるよう支援します。

## なぜ知序を作ったのか

> **知序が解決するのは、情報取得の問題ではなく、知識の組織化と学習の意思決定の問題です。**

### ある学生のリアルな場面

期末試験の前に、ある学生の手元には 8 つの PDF 講義資料、1 冊の教科書、そして数十問の練習問題がありました。彼が 1 問を AI に質問すると、AI はすぐに正解を返しました——しかし彼には依然として分かりませんでした。その問題がどの前提知識に関わるのか、自分はどの段階でつまずいているのか、次に何を復習すべきなのか。

従来の AI は「1 つの問題」に答えるのが得意ですが、学生が本当に必要としているのは「講義全体」を理解し、継続的に成長する方法を知ることです。

### 核心的な課題：資料は増える一方で、知識はますます断片化していく

| 問題 | 具体的な現れ |
| --- | --- |
| **全体像が見えない** | 多くの内容を学んだのに、知識ポイント同士のつながりが分からない |
| **盲点が見つからない** | 問題を間違えても答えが違うと分かるだけで、どの基礎知識が欠けているのか分からない |
| **次の一歩が分からない** | 大量の資料を前にして、復習の順序と学習の重点を決められない |

### 位置づけ：「PDF をアップロード → AI が要約」ではない

> 従来の AI は文書を要約できますが、次のことは教えてくれません：
> 「ポインタが理解できないのは、メモリアドレスをまだ本当に理解していないからです。」

知序は、学びを「1 つの問題を解く」ことから「一人の人間の知識世界を理解する」ことへと広げたいと考えています：

- 講義資料を**探索可能なナレッジグラフ**に変える（知識ポイント + 前提 / 関連 / 包含関係）
- AI の質疑応答を**あなたの講義資料に基づいて**行い、ファイル名とページ番号まで遡れるようにする
- クイズと前提関係を通じて**盲点を特定**し、**次に何を学ぶべきか**を導き出す

### 汎用 AI チャットとの違い

| | 汎用 AI チャット | 知序 |
| --- | --- | --- |
| 目標 | 個々の問題に答える | 講義全体の知識構造を提示する |
| コンテキスト | 貼り付けた内容だけを読む | あなたのすべての講義資料を、ページ番号まで遡って参照 |
| 誤答 | 正しい答えを提示する | 具体的な知識ポイントに関連付け、習熟度と学習パスに反映 |
| 学習の推進 | 一度きりの回答 | 前提関係に基づいて個別最適化された学習パスを生成 |

### 対象となる人

**長期的に学び続ける人**——知識体系を築きたい人を対象としています。現在は C 言語の 1 コースを対象としていますが、今後は高等数学、物理、線形代数などの科目へ拡張でき、最終的には**学校独自の AI 学習プラットフォーム**となることを目指しています。

> すべての学生が自分自身の知識体系を持ち、学びを学生自身の手に取り戻せるように。

## コア機能

| モジュール | 説明 |
| --- | --- |
| **コース管理と資料アップロード** | コースの作成/編集/削除；PDF、DOCX、PPTX、TXT、Markdown のアップロード；**アップロードは即座に応答し、バックグラウンドで非同期に解析**；ページが自動的に進捗をポーリング（処理待ち / 解析中 / 知識抽出中 / 完了 / 処理失敗）；章とページ番号を自動的に保持し、チャンク単位で保存 |
| **AI ナレッジグラフ生成** | 知識ポイントと関係を抽出（定義、章、難易度、出典、前提/関連/包含/実例関係）；構造化 JSON で保存；知識ポイントを重複排除；デフォルトで「未確認」としてマーク；手動での追加・削除・編集をサポート |
| **インタラクティブなナレッジグラフ** | React Flow キャンバス：ノードのドラッグ、ズーム、パン、検索、章/関係によるフィルタリング、関連ハイライト、前提知識の表示、階層レイアウト；青=習得済み、黄=学習中、赤=復習が必要、灰=未学習；ノードをクリックすると詳細パネルを表示 |
| **AI 個別学習アシスタント** | 講義資料に基づく RAG 質疑応答で、出典ファイルとページ番号を明示；知識ポイントの解説（わかりやすい/詳細/例示/類推/コード）；ソクラテス式の誘導；関連するナレッジグラフへのジャンプ |
| **知識の盲点診断とクイズ** | 単一選択/複数選択/正誤/記述/コード問題；各問題を知識ポイントに関連付け；採点後に解説と想定される誤解を提示；習得状態を更新 |
| **個別最適化された学習パス** | 前提関係のトポロジカルソートに基づいて学習順序を生成；習得済みの知識ポイントは自動的にスキップ；進捗記録と完了フィードバック |

## 技術スタック

- **フロントエンド**：Next.js 15（App Router）、React 19、TypeScript、Tailwind CSS、shadcn スタイルのコンポーネント、`@xyflow/react`（React Flow）、Lucide アイコン
- **バックエンド**：Next.js Route Handlers（Node.js runtime）
- **データベース**：
  - ローカル開発：**SQLite**（Node 24 内蔵の `node:sqlite`、ネイティブ依存ゼロ）
  - 本番（ルート A）：**SQLite + 永続ボリューム**。`DATA_DIR` でマウントボリュームを指定し、ほぼ改修なしでデプロイ可能
  - 本番（ルート B、大規模化）：**Supabase / PostgreSQL**（移行 SQL は `supabase/migrations/` を参照）
- **デプロイ**：Docker（[`Dockerfile`](Dockerfile) を参照）+ 常駐プロセスと永続ボリュームをサポートする任意のプラットフォーム（Railway / Render / Fly.io など）
- **AI**：OpenAI-compatible インターフェース（任意のプロバイダーを設定可能）、サーバーサイド呼び出し、構造化出力 + zod 検証、内蔵デモエンジンによるフォールバック
- **文書解析**：`unpdf`（PDF）、`mammoth`（DOCX）、`jszip`（PPTX）

## クイックスタート（ローカル実行）

### 環境要件

- Node.js ≥ 22.5（24 を推奨、`node:sqlite` 内蔵）
- npm（または pnpm / yarn）

### 手順

```bash
# 1. 依存関係をインストール
npm install
# （pnpm でも可：pnpm install）

# 2.（任意）AI モデルを設定。下記の「AI モデル設定」を参照
#   設定しなくても実行可能で、自動的に「デモモード」になります

# 3. 開発サーバーを起動
npm run dev
```

<http://localhost:3000> を開けば使用できます。初回アクセス時はログインページにリダイレクトされ、内蔵のデモアカウントを利用できます：

- **メールアドレス**：`demo@zhixu.app`
- **パスワード**：`demo123`

「登録」をクリックして自分のアカウントを作成することもできます。初回起動時には自動的にテーブルが作成され、**デモコース「C 言語プログラミング」**（ナレッジグラフ、クイズ、学習記録、学習パスを含む）が書き込まれるため、すぐに一連の流れを体験できます。

### よく使うコマンド

```bash
npm run dev        # 開発サーバー（自動コンパイル、コード変更が即時反映）
npm run build      # 本番ビルド
npm start          # 本番ビルドを実行（事前に npm run build が必要）
npm run typecheck  # TypeScript 型チェック
npm run lint       # ESLint
```

> ⚠️ **`npm run dev` と `npm start` を同時に実行しないでください**：両者は同じ `.next` ディレクトリを共有しており、
> dev モードがそれを開発用の成果物に書き換えるため、稼働中の本番サーバーは自分のビルドファイルを見つけられなくなります。
> その結果、**ページは表示されてもすべての静的リソースが 400 になり、ボタンがすべて機能しなくなり、`client-side exception` が発生します**。
>
> 実行方法を切り替える際は、次の順序で操作してください：
> 1. 現在のサーバーを停止する（`Ctrl + C`）
> 2. `.next` を削除する
> 3. 必要に応じて `npm run dev` を実行するか、`npm run build` の後に `npm start` を実行する
>
> 同様に、**サーバー稼働中に `npm run build` を実行しないでください**。

### 一連の流れを体験する

1. トップページを開き、「C 言語プログラミング」コースに入ります。
2. 「ナレッジグラフ」をクリックし、ノードをドラッグ/ズーム/クリックして詳細を確認します。
3. 「AI チューター」に進み、たとえば *「malloc と free の役割は何ですか？」* と質問します。
4. 「クイズ」に進み、クイズを生成して回答し、送信後に習得状態の変化を確認します。
5. 「学習パス」に進み、目標の知識ポイント「動的メモリ割り当て」を選択し、自動導出された学習順序を確認します。
6. コース詳細ページの「資料アップロード」で任意の PDF をアップロードし、解析と知識抽出の結果を確認します。

## ユーザーログインとアカウント

知序には**ローカルアカウントシステム**が内蔵されており、すぐに使えて外部サービスは不要です：

- 登録 / ログイン / ログアウト。パスワードは Node 内蔵の `scrypt` によるソルト付きハッシュで保存
- httpOnly Cookie ベースのセッション（有効期限 30 日）。ミドルウェアが未ログインのリクエストを一括で遮断
- すべてのコース、資料、ナレッジグラフ、学習記録をユーザーごとに分離（相互に不可視）
- 各ユーザーは「設定」ページで自分の AI モデルを設定可能（相互に干渉しない）

> 本番環境では **Supabase Auth** へスムーズに移行できます。`profiles` テーブルは `auth.users(id)` を前提に設計済みで、認証レイヤーとデータアクセスアダプターを差し替えるだけです（詳細は「Supabase + Vercel へのデプロイ」を参照）。

## AI モデル設定

設定方法は**2 通り**あり、優先度は高い順に次のとおりです：

1. **画面からの設定（推奨）**：ログイン後、「設定」ページで API Key、エンドポイント URL、モデルを入力して保存すると即座に反映されます。ユーザーごとに分離して保存されます。
2. **環境変数**：`.env.example` を `.env.local` にコピーして入力します：

```env
# OpenAI-compatible インターフェース（任意の互換サービスに変更可能）
AI_API_KEY=sk-xxxx
AI_BASE_URL=https://api.openai.com/v1
AI_MODEL=gpt-4o-mini
# 任意：知識抽出にはより高速/安価なモデルを使用
AI_EXTRACT_MODEL=
# 任意：1 回の応答の最大出力 token。推論系モデルはまず大量の token を思考に消費するため、
# AI チューターが時々デモモードにフォールバックする場合は、この値を大きくしてください（デフォルト 8192）
AI_MAX_TOKENS=8192
# 任意：構造化 JSON 呼び出し（知識抽出）の最大出力 token（デフォルト 16000）
AI_EXTRACT_MAX_TOKENS=16000
# 任意：1 リクエストのタイムアウト（ミリ秒、デフォルト 300000）
AI_TIMEOUT_MS=300000
# 任意：429 / 5xx / ネットワークエラー時のリトライ回数（デフォルト 2）
AI_MAX_RETRIES=2
# 任意：1 に設定すると Base URL のローカル/イントラネット向けを禁止（SSRF 対策）。Ollama 使用時は 0 のまま
AI_BLOCK_PRIVATE_BASE_URL=0
```

アップロードとバックグラウンド処理関連（任意）：

```env
# アップロードサイズ上限（MB、デフォルト 100）
MAX_UPLOAD_SIZE_MB=100
# 単一ドキュメントのバックグラウンド処理タイムアウト（ミリ秒、デフォルト 1800000 = 30 分）
# タイムアウトしたドキュメントは失敗としてマークされ、キューは次の処理へ進み、永久に停止することを防ぎます
DOC_PROCESS_TIMEOUT_MS=1800000
# データディレクトリ：デプロイ時は永続ボリュームを指定（ローカルではデフォルト ./data）
DATA_DIR=/data
```

任意の **OpenAI-compatible** サービス（OpenAI、DeepSeek、Moonshot、Qwen、ローカル Ollama など）をサポートします。`AI_BASE_URL` と `AI_MODEL` を変更するだけです。モデル呼び出しはすべてサーバーサイドで行われます。

### 接続の詳細とセキュリティ

- **API Key はフロントエンドに返されません**：設定ページには「設定済みかどうか」とマスクされたプレビュー（例：`sk-…abcd`）だけが表示され、API から完全な Key が送信されることはありません。
- **接続のセルフチェック**：設定ページの「接続テスト」ボタンは実際にモデル API を 1 回呼び出し、所要時間または具体的なエラー（Key 無効 / Base URL エラー / モデルが存在しない / レート制限など）を返します。
- **自動リトライ**：429、5xx、ネットワークエラー時は指数バックオフで自動リトライします（デフォルト 2 回）。
- **パラメータ互換性**：一部の新しいモデルは `max_tokens` ではなく `max_completion_tokens` を要求するため、自動的にこのパラメータに切り替えてリトライします。
- **失敗の可視化**：AI 呼び出しが失敗してデモエンジンにフォールバックした場合、資料カードに黄色のヒントが表示され、黙ってフォールバックすることはありません。
- **Base URL の検証**：`http(s)://` で始まる完全なアドレスである必要があります。マルチユーザー環境では `AI_BLOCK_PRIVATE_BASE_URL=1` を設定してイントラネット向けを禁止できます（SSRF 対策）。
- ⚠️ **Key の保存**：ユーザー単位の Key はローカル SQLite（`user_settings` テーブル）に平文で保存されます。ローカルでのセルフホストなら許容範囲ですが、複数人に提供する場合は環境変数からのみ Key を注入するか、データベースの暗号化とアクセス制御を行うことを推奨します。

### 各機能の AI 動作

| 機能 | Key あり | Key なし（デモモード） |
| --- | --- | --- |
| 知識抽出 | LLM による構造化出力（zod 検証） | 内蔵用語集によるヒューリスティック抽出、画面に「デモエンジン」と表示 |
| AI チューター | RAG 検索 + LLM 生成 | キーワード検索 + テンプレート応答、大規模モデルではないことを明示 |
| 出題 | LLM による出題 | ルールベース出題、「デモエンジン」と表示 |

## デモモードの説明

**デモモードは偽装されたフェイクデータではありません。** `AI_API_KEY` が未設定の場合：

- 知識抽出は**内蔵用語集 + 共起関係**に基づく決定論的ルールエンジンを使用し、すべての出力は `verified=false`（未確認）、低信頼度となり、画面に明確に表示されます。
- AI チューターの応答は**キーワード検索 + テンプレート**で生成され、応答の末尾に「デモルールエンジンによる生成」と明記されます。
- 内蔵デモコースのナレッジグラフは**手作業で作成**したサンプルデータであり、製品形態を示すためのもので、実際の AI 分析を表すものではありません。

`AI_API_KEY` を設定すると、上記の機能は自動的に実際の大規模モデルに切り替わります。

## デプロイ（ルート A：永続ボリューム）

チーム / 小規模利用に適しています：**SQLite + ローカルファイルストレージを維持**し、データディレクトリを永続ボリュームにマウントするだけで、ほぼ改修なしに公開できます。
完全な手順は [`DEPLOY.md`](DEPLOY.md) を参照してください。核心は次の 3 ステップです：

1. [`Dockerfile`](Dockerfile) でイメージをビルドする（またはプラットフォームに自動認識させる）
2. 永続ボリュームを `/data` にマウントし、`DATA_DIR=/data` を設定する
3. AI 環境変数を設定し、公開ドメインを生成する

```bash
docker build -t zhixu .
docker run -d -p 3000:3000 -v zhixu-data:/data -e DATA_DIR=/data \
  -e AI_BASE_URL=https://api.deepseek.com -e AI_MODEL=deepseek-chat -e AI_API_KEY=sk-xxxx zhixu
```

> 文書処理は**バックグラウンド非同期**に変更されました：アップロード API は即座に応答し、バックグラウンドでキューに従って解析と知識抽出を行い、フロントエンドが状態をポーリングします。
> プロセス再起動後、前回未完了だった文書タスクは自動的に復旧します。
>
> 推奨プラットフォーム：Railway / Render / Fly.io（いずれも常駐プロセス + 永続ボリュームをサポート）。

## Supabase + Vercel へのデプロイ（ルート B）

ユーザー規模が大きくなり、複数インスタンスの水平スケーリングが必要になった段階でこのルートを選択します（改修コストは高く、データ層とファイルストレージの置き換えが必要です）：

1. Supabase でプロジェクトを作成し、SQL Editor で `supabase/migrations/0001_init.sql` を実行します（任意で `0002_vector.sql` も実行）。
2. ファイルストレージ用に Supabase Storage を設定します。
3. Vercel に本プロジェクトをデプロイし、環境変数を設定します：

```env
NEXT_PUBLIC_SUPABASE_URL=...
NEXT_PUBLIC_SUPABASE_ANON_KEY=...
SUPABASE_SERVICE_ROLE_KEY=...
DATABASE_URL=...
AI_API_KEY=...
AI_BASE_URL=https://api.openai.com/v1
AI_MODEL=gpt-4o-mini
```

> 説明：現在のコードのローカルデータアクセス層は SQLite をランタイムストレージとしています。ルート B では `src/lib/db/repo.ts` を Supabase Client ベースの実装に置き換える必要があります（Schema と移行 SQL は完全に整合しており、シームレスに置き換え可能）。ファイルアップロードは Supabase Storage に変更し、バックグラウンドタスクキューを補完します（Serverless 環境ではプロセスが常駐しないため）。

## 既知の問題と今後の最適化

- **ローカル SQLite と本番 PostgreSQL の差異**：ローカルでは `node:sqlite`（同期 API）を使用し、本番では Supabase クライアント実装に置き換える必要があります。統一されたリポジトリインターフェースを導入することでさらに抽象化できます。
- **大容量ファイル解析による CPU 消費**：1000 ページ以上の PDF を解析する際、一時的にイベントループを占有し、その間ほかのリクエストが遅くなる可能性があります。複数人による同時アップロードが想定される場合は、解析を worker スレッドに移すことを推奨します。
- **クロス言語検索**：中国語の質問に対する英語教材のチャンク検索のヒット率が弱い（知識ノードのコンテキストでフォールバック可能）。ベクトル検索を導入すれば解決できます。
- **キーワード検索の限界**：中国語 bigram + BM25 により分かち書きと再現率は大幅に改善しましたが、同義語/意味的マッチングは依然として弱く、pgvector を導入すればさらに改善できます。
- **習熟度スコア**：現在は透明性のあるルール採点です。今後、設問難易度による重み付け、反復テストの成績、忘却曲線（間隔反復）を組み合わせてさらに最適化できます。
- **グラフのパフォーマンス**：知識ポイントの規模が非常に大きい場合（500 ノード超）、React Flow のレンダリングには仮想化と増分レイアウトの導入が必要です。
