# 知序 Zhixu

**AI-Powered Knowledge Graph & Learning Companion**

> 지식을 파편에서 체계로, 학습을 수동적 수용에서 능동적 탐구로.

[简体中文](README.md) · [English](README.en.md) · [日本語](README.ja.md) · **한국어**

> **현재 버전: v2.2.0** — 버전 기록은 [CHANGELOG.md](CHANGELOG.md)를 참고하십시오.

知序는 **AI 지식 그래프**를 핵심으로 하는 개인화 학습 플랫폼입니다. 흩어진 강의 자료(PDF / DOCX / PPTX / TXT / Markdown)를 시각화되고 탐색 가능하며 추적 가능한 지식 체계로 전환하고, 지식 사각지대 진단과 개인화 학습 경로를 통해 학생이 지식 간의 연결을 진정으로 이해하도록 돕습니다.

## 왜 知序를 만드는가

> **知序가 해결하는 것은 정보 획득의 문제가 아니라, 지식의 조직과 학습 의사결정의 문제입니다.**

### 실제 학생의 한 장면

기말고사를 앞둔 한 학생에게는 PDF 강의자료 8개, 교재 한 권, 그리고 수십 개의 연습 문제가 있습니다. 그는 문제 하나를 AI에게 가져가 묻고, AI는 곧바로 정답을 내놓습니다. 그러나 그는 여전히 알지 못합니다. 이 문제가 어떤 선수 지식과 관련되는지, 자신이 정확히 어느 단계를 배우지 못했는지, 다음에 무엇을 복습해야 하는지를.

기존 AI는 '하나의 질문'에 답하는 데 능숙하지만, 학생에게 정말 필요한 것은 '한 과목 전체'를 이해하고 어떻게 꾸준히 발전할지를 아는 것입니다.

### 핵심 고통: 자료는 늘어나는데 지식은 더 파편화된다

| 문제 | 구체적 양상 |
| --- | --- |
| **전체 그림을 볼 수 없음** | 많은 내용을 배웠지만 지식점들 사이에 어떤 연결이 있는지 모릅니다 |
| **사각지대를 찾을 수 없음** | 문제를 틀려도 답이 틀렸다는 것만 알 뿐, 어떤 기초 지식점이 빠졌는지 분명하지 않습니다 |
| **다음 단계를 모름** | 방대한 자료 앞에서 복습 순서와 학습 우선순위를 정할 수 없습니다 |

### 포지셔닝: 'PDF 업로드에서 AI 요약'이 아니다

> 기존 AI는 문서를 요약해 주지만, 다음과 같은 것은 알려주지 않습니다.
> "포인터를 배우지 못한 것은 메모리 주소를 아직 진정으로 이해하지 못했기 때문입니다."

知序는 학습을 '하나의 문제 해결'에서 '한 사람의 지식 세계 이해'로 확장하고자 합니다.

- 강의 자료를 **탐색 가능한 지식 그래프**로 전환합니다(지식점 + 선수 / 관련 / 포함 관계)
- AI 질의응답이 **당신의 강의 자료에 근거하여** 답하고, 파일명과 페이지까지 추적할 수 있게 합니다
- 퀴즈와 선수 관계를 통해 **사각지대를 찾아내고**, **다음에 무엇을 배워야 하는지** 도출합니다

### 일반 AI 대화와의 차이

| | 일반 AI 대화 | 知序 |
| --- | --- | --- |
| 목표 | 단일 질문에 답변 | 한 과목 전체의 지식 구조 제시 |
| 컨텍스트 | 붙여 넣은 것만 읽음 | 당신의 모든 강의 자료, 페이지까지 추적 가능 |
| 오답 | 정답 제시 | 구체적 지식점과 연결되어 숙달도와 학습 경로에 영향 |
| 학습 진행 | 일회성 답변 | 선수 관계에 따른 개인화 학습 경로 생성 |

### 누구를 위한 것인가

**장기 학습자**, 즉 지식 체계를 세워야 하는 사람을 위한 것입니다. 오늘은 C 언어 한 과목에 쓰이지만, 이후 고등수학, 물리, 선형대수 등 과목으로 확장할 수 있으며, 궁극적으로는 **학교 자체의 AI 학습 플랫폼**이 되고자 합니다.

> 모든 학생이 자신만의 지식 체계를 갖게 하고, 학습을 학생에게 돌려줍니다.

## 기술 스택

- **프론트엔드**: Next.js 15(App Router), React 19, TypeScript, Tailwind CSS, shadcn 스타일 컴포넌트, `@xyflow/react`(React Flow), Lucide 아이콘
- **백엔드**: Next.js Route Handlers(Node.js runtime)
- **데이터베이스**:
  - 로컬 개발: **SQLite**(Node 24 내장 `node:sqlite`, 네이티브 의존성 없음)
  - 프로덕션(경로 A): **SQLite + 영구 볼륨**, `DATA_DIR`로 마운트된 볼륨을 지정하면 거의 수정 없이 배포 가능
  - 프로덕션(경로 B, 규모 확장): **Supabase / PostgreSQL**(마이그레이션 SQL은 `supabase/migrations/` 참고)
- **배포**: Docker([`Dockerfile`](Dockerfile) 참고) + 상시 프로세스와 영구 볼륨을 지원하는 모든 플랫폼(Railway / Render / Fly.io 등)
- **AI**: OpenAI-compatible 인터페이스(임의의 공급자 설정 가능), 서버 측 호출, 구조화 출력 + zod 검증, 내장 데모 엔진 폴백
- **문서 파싱**: `unpdf`(PDF), `mammoth`(DOCX), `jszip`(PPTX)

## 로컬에서 빠른 시작

### 환경 요구 사항

- Node.js ≥ 22.5(24 권장, `node:sqlite` 내장)
- npm(또는 pnpm / yarn)

### 단계

```bash
# 1. 의존성 설치
npm install
# (pnpm 사용도 가능: pnpm install)

# 2. (선택) AI 모델 설정, 아래 "AI 모델 설정" 참고
#   설정하지 않아도 실행되며, 자동으로 "데모 모드"로 진입합니다

# 3. 개발 서버 시작
npm run dev
```

<http://localhost:3000>을 열면 사용할 수 있습니다. 첫 방문 시 로그인 페이지로 이동하며, 내장 데모 계정을 사용할 수 있습니다.

- **이메일**: `demo@zhixu.app`
- **비밀번호**: `demo123`

'회원가입'을 클릭해 자신의 계정을 만들 수도 있습니다. 첫 실행 시 테이블이 자동으로 생성되고 **데모 강의 "C 언어 프로그래밍"**(지식 그래프, 퀴즈, 학습 기록, 학습 경로 포함)이 기록되어, 설치 직후 전체 흐름을 체험할 수 있습니다.

### 자주 쓰는 명령

```bash
npm run dev        # 개발 서버(자동 컴파일, 코드 변경 즉시 반영)
npm run build      # 프로덕션 빌드
npm start          # 프로덕션 빌드 실행(npm run build 선행 필요)
npm run typecheck  # TypeScript 타입 검사
npm run lint       # ESLint
```

> ⚠️ **`npm run dev`와 `npm start`를 동시에 실행하지 마십시오**: 두 명령이 같은 `.next` 디렉터리를 공유하므로,
> dev 모드가 이를 개발 산출물로 덮어쓰면 실행 중인 프로덕션 서버는 곧 자신의 빌드 파일을 찾지 못하고,
> **페이지는 표시되지만 모든 정적 리소스가 400을 반환하고 버튼이 모두 동작하지 않으며 `client-side exception` 오류가 발생**합니다.
>
> 실행 방식을 전환할 때는 다음 순서를 지키십시오.
> 1. 현재 서버 중지(`Ctrl + C`)
> 2. `.next` 삭제
> 3. 필요에 따라 `npm run dev`를 실행하거나, `npm run build` 후 `npm start`를 실행
>
> 마찬가지로 **서버가 실행 중인 동안에는 `npm run build`를 실행하지 마십시오**.

### 전체 흐름 체험하기

1. 홈페이지를 열고 "C 언어 프로그래밍" 강의에 들어갑니다.
2. "지식 그래프"를 클릭하고, 드래그/확대/노드 클릭으로 상세 정보를 확인합니다.
3. "AI 튜터"에 들어가 질문합니다. 예: *"malloc과 free의 역할은 무엇인가요?"*
4. "퀴즈"에 들어가 퀴즈를 생성하고 응답한 뒤, 제출 후 숙달 상태 변화를 확인합니다.
5. "학습 경로"에 들어가 목표 지식점 "동적 메모리 할당"을 선택하고 자동으로 도출된 학습 순서를 확인합니다.
6. 강의 상세 페이지에서 "자료 업로드"로 임의의 PDF를 업로드하고, 파싱과 지식 추출 결과를 관찰합니다.

## 사용자 로그인과 계정

知序는 **로컬 계정 체계**를 내장하여, 별도의 외부 서비스 없이 바로 사용할 수 있습니다.

- 회원가입 / 로그인 / 로그아웃, 비밀번호는 Node 내장 `scrypt`로 솔트 해시하여 저장
- httpOnly Cookie 기반 세션(30일 유효), 미들웨어에서 미로그인 요청을 일괄 차단
- 모든 강의, 자료, 지식 그래프, 학습 기록이 사용자별로 격리(서로 볼 수 없음)
- 각 사용자는 "설정" 페이지에서 자신의 AI 모델을 설정할 수 있음(서로 간섭 없음)

> 프로덕션 환경에서는 **Supabase Auth**로 원활하게 업그레이드할 수 있습니다. `profiles` 테이블은 이미 `auth.users(id)` 기준으로 설계되어 있어, 인증 계층과 데이터 접근 어댑터만 교체하면 됩니다(자세한 내용은 "경로 B: Supabase와 Vercel 배포" 참고).

## AI 모델 설정

설정 방법은 **두 가지**이며, 우선순위는 높은 순서대로 다음과 같습니다.

1. **화면 설정(권장)**: 로그인 후 "설정" 페이지에서 API Key, 엔드포인트 주소, 모델을 입력하고 저장하면 즉시 적용되며, 사용자별로 격리 저장됩니다.
2. **환경 변수**: `.env.example`을 `.env.local`로 복사하고 다음과 같이 입력합니다.

```env
# OpenAI-compatible 인터페이스(호환되는 임의의 서비스 제공자로 교체 가능)
AI_API_KEY=sk-xxxx
AI_BASE_URL=https://api.openai.com/v1
AI_MODEL=gpt-4o-mini
# 선택: 지식 추출에 더 빠르고 저렴한 모델 사용
AI_EXTRACT_MODEL=
# 선택: 1회 응답의 최대 출력 token. 추론형 모델은 사고에 많은 token을 먼저 소모하므로,
# AI 튜터가 간혹 데모 모드로 폴백된다면 이 값을 늘리십시오(기본값 8192)
AI_MAX_TOKENS=8192
# 선택: 구조화 JSON 호출(지식 추출)의 최대 출력 token(기본값 16000)
AI_EXTRACT_MAX_TOKENS=16000
# 선택: 1회 요청 타임아웃 밀리초(기본값 300000)
AI_TIMEOUT_MS=300000
# 선택: 429 / 5xx / 네트워크 오류의 재시도 횟수(기본값 2)
AI_MAX_RETRIES=2
# 선택: 1로 설정하면 Base URL이 로컬/내부망을 가리키는 것을 차단(SSRF 방지). Ollama 사용 시 0 유지
AI_BLOCK_PRIVATE_BASE_URL=0
```

업로드와 백그라운드 처리 관련(선택):

```env
# 업로드 크기 상한(MB, 기본값 100)
MAX_UPLOAD_SIZE_MB=100
# 단일 문서의 백그라운드 처리 타임아웃(밀리초, 기본값 1800000 = 30분)
# 타임아웃 시 해당 문서를 실패로 표시하고 큐는 다음 문서를 계속 처리하여 영구 정체를 방지
DOC_PROCESS_TIMEOUT_MS=1800000
# 데이터 디렉터리: 배포 시 영구 볼륨을 지정(로컬 기본값 ./data)
DATA_DIR=/data
```

**OpenAI-compatible** 서비스(OpenAI, DeepSeek, Moonshot, Qwen, 로컬 Ollama 등)를 모두 지원하며, `AI_BASE_URL`과 `AI_MODEL`만 수정하면 됩니다. 모델 호출은 전부 서버 측에서 수행됩니다.

### 연동 세부 사항과 보안

- **API Key는 프론트엔드로 반환되지 않음**: 설정 페이지는 "설정 여부"와 마스킹된 미리보기(예: `sk-…abcd`)만 표시하며, API는 완전한 Key를 절대 전송하지 않습니다.
- **연결 자가 점검**: 설정 페이지의 "연결 테스트" 버튼은 실제로 모델 API를 한 번 호출하고, 소요 시간이나 구체적 오류(Key 무효 / Base URL 오류 / 모델 없음 / 레이트 리밋 등)를 반환합니다.
- **자동 재시도**: 429, 5xx, 네트워크 오류는 지수 백오프로 자동 재시도합니다(기본 2회).
- **파라미터 호환성**: 일부 최신 모델은 `max_tokens` 대신 `max_completion_tokens`를 요구하므로, 자동으로 해당 파라미터로 전환해 재시도합니다.
- **실패 가시성**: AI 호출이 실패해 데모 엔진으로 폴백될 때 자료 카드에 노란색 안내가 표시되며, 조용히 폴백되지 않습니다.
- **Base URL 검증**: `http(s)://`로 시작하는 완전한 주소여야 하며, 다중 사용자 배포에서는 `AI_BLOCK_PRIVATE_BASE_URL=1`로 내부망 지정을 차단(SSRF 방지)할 수 있습니다.
- ⚠️ **Key 저장**: 사용자 수준 Key는 로컬 SQLite(`user_settings` 테이블)에 평문으로 저장됩니다. 로컬 자체 호스팅에서는 허용 가능하지만, 여러 사람에게 배포하는 경우 환경 변수로만 Key를 주입하거나 데이터베이스 암호화와 접근 제어를 적용할 것을 권장합니다.

## 데모 모드 설명

**데모 모드는 위장한 가짜 데이터가 아닙니다.** `AI_API_KEY`가 설정되지 않은 경우:

- 지식 추출은 **내장 용어집 + 동시 출현 관계** 기반의 결정적 규칙 엔진을 사용하며, 모든 산출물은 `verified=false`(확인 대기)와 낮은 신뢰도로 표시되고 화면에 명확히 표기됩니다.
- AI 튜터 응답은 **키워드 검색 + 템플릿**으로 생성되며, 응답 끝에 "데모 규칙 엔진이 생성함"이 명시됩니다.
- 내장 데모 강의의 지식 그래프는 **수작업으로 작성한** 예시 데이터로, 제품 형태를 보여주기 위한 것이며 실제 AI 분석을 의미하지 않습니다.

`AI_API_KEY`를 설정하면 위 기능은 자동으로 실제 대규모 모델로 전환됩니다.

## 경로 A: 영구 볼륨 배포

팀 / 소규모 사용에 적합합니다. **SQLite + 로컬 파일 저장을 유지**하고 데이터 디렉터리만 영구 볼륨에 마운트하면, 거의 수정 없이 배포할 수 있습니다.
전체 절차는 [`DEPLOY.md`](DEPLOY.md)를 참고하십시오. 핵심은 세 단계입니다.

1. [`Dockerfile`](Dockerfile)로 이미지 빌드(또는 플랫폼이 자동 인식하도록 함)
2. 영구 볼륨을 `/data`에 마운트하고 `DATA_DIR=/data` 설정
3. AI 환경 변수 설정, 공개 도메인 생성

```bash
docker build -t zhixu .
docker run -d -p 3000:3000 -v zhixu-data:/data -e DATA_DIR=/data \
  -e AI_BASE_URL=https://api.deepseek.com -e AI_MODEL=deepseek-chat -e AI_API_KEY=sk-xxxx zhixu
```

> 문서 처리는 **백그라운드 비동기**로 변경되었습니다. 업로드 API는 즉시 반환하고, 백그라운드에서 큐에 따라 파싱과 지식 추출을 수행하며, 프론트엔드는 상태를 폴링합니다.
> 프로세스가 재시작되면 이전에 완료되지 않은 문서 작업이 자동으로 복구됩니다.
>
> 플랫폼 추천: Railway / Render / Fly.io(모두 상시 프로세스 + 영구 볼륨 지원).

## 경로 B: Supabase와 Vercel 배포

사용자 규모가 커져 다중 인스턴스 수평 확장이 필요할 때 이 경로를 사용합니다(개조 비용이 높으며, 데이터 계층과 파일 저장을 교체해야 합니다).

1. Supabase에서 프로젝트를 생성하고, SQL Editor에서 `supabase/migrations/0001_init.sql`을 실행합니다(선택적으로 `0002_vector.sql`도 실행).
2. 파일 저장을 위해 Supabase Storage를 설정합니다.
3. Vercel에 본 프로젝트를 배포하고 환경 변수를 설정합니다.

```env
NEXT_PUBLIC_SUPABASE_URL=...
NEXT_PUBLIC_SUPABASE_ANON_KEY=...
SUPABASE_SERVICE_ROLE_KEY=...
DATABASE_URL=...
AI_API_KEY=...
AI_BASE_URL=https://api.openai.com/v1
AI_MODEL=gpt-4o-mini
```

> 설명: 현재 코드의 로컬 데이터 접근 계층은 SQLite를 런타임 저장소로 사용합니다. 경로 B에서는 `src/lib/db/repo.ts`를 Supabase Client 기반 구현으로 교체해야 하며(Schema와 마이그레이션 SQL이 이미 완전히 정렬되어 있어 원활히 교체 가능), 파일 업로드는 Supabase Storage로 변경하고 백그라운드 작업 큐를 보완해야 합니다(Serverless 환경에서는 프로세스가 상주하지 않음).

## 알려진 문제와 향후 최적화

- **로컬 SQLite와 프로덕션 PostgreSQL의 차이**: 로컬은 `node:sqlite`(동기 API)를 사용하며, 프로덕션에서는 Supabase 클라이언트 구현으로 교체해야 합니다. 통일된 리포지토리 인터페이스를 도입해 더 추상화할 수 있습니다.
- **대용량 파일 파싱의 CPU 점유**: 1000페이지 이상의 PDF를 파싱할 때 이벤트 루프를 잠시 점유하여 다른 요청이 느려질 수 있습니다. 다중 동시 업로드 시나리오에서는 파싱을 worker 스레드에 넣는 것을 권장합니다.
- **교차 언어 검색**: 중국어 질문이 영어 교재 청크에 대한 검색 적중이 약합니다(지식 노드 컨텍스트로 보완 가능). 벡터 검색을 연동하면 해결됩니다.
- **키워드 검색의 한계**: 중국어 bigram + BM25로 분절과 재현율은 크게 개선했지만, 동의어/의미 매칭은 여전히 약합니다. pgvector를 배포하면 더 향상시킬 수 있습니다.
- **숙달도 점수**: 현재는 투명한 규칙 기반 점수이며, 이후 문제 난이도 가중치, 반복 테스트 성과, 망각 곡선(간격 반복)을 결합해 더 최적화할 수 있습니다.
- **차트 성능**: 지식점 규모가 매우 클 때(500개 초과 노드) React Flow 렌더링에는 가상화와 증분 레이아웃이 필요합니다.
